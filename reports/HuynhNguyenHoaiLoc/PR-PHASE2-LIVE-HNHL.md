# HNHL Phase 2 live — ESP32 entry segmentation, face decisions and queue hand-off

Phase2Pipeline previously required an already segmented entry. This change supplies the ESP32 MJPEG processing loop, incremental entry segmentation and real model inputs so door observations can reach the existing queue/state machine.

- Add `DoorMonitor` and `tools.monitor_door` with a single receiver, a configurable 5 Hz schedule, per-track N/M entry boundaries, bounded top-K face samples, frontal/quality selection, same-identity majority verification and completed-track suppression. Ambiguous associations abstain. Stream loss, reconnect, reset and resize interrupt incomplete evidence.
- Use YOLO/person tracking and real OSNet, sharing its encoder with the pipeline. Preserve single-embedding callers while adding multi-frame verification, entry provenance and enqueue/event timestamps sampled after inference. Reuse face sharpness and face/person association in D2 tooling. Supply optional face landmarks and local InsightFace root configuration.
- Add guided five-pose ESP32 enrolment, private JSONL logs, timestamped/hash-validated replay, optional overlay video/snapshots and an evaluator for reviewed entry truth. Metrics retain missing/unresolved attempts and distinguish FAR over decided impostors from all attempts. Logs and biometric data stay under ignored `data/`.
- Record HNHL ownership in the plan, provide KR's shared-object integration contract and update issue #111's perception status with DQK's attributed RTX4050 workload results and chair-width proposal.

Validation includes 762 CPU/replay tests passing, two missing-data skips and four GPU tests deselected. 46 targeted tests cover enrolment and monitoring. Guided ESP32 enrolment completed all five poses for P01. After correcting camera placement, two separate 90 s live runs on HNHL's RTX5060 produced three P01 authorizations and three impostor queue events, with no false queue/authorization observed in those decisions. The user confirmed a P01-only run and a separate unenrolled-person run with three physical walk-ins. Both streams had zero reconnects. The first intruder became active and the next two remained FIFO, with queue lengths 0/1/2. Entry-start-to-enqueue latency was 9.387/9.355/10.245 s, including entry observation and completion time.

Retain all five unresolved and one interrupted segment across the two runs. Each cohort contains six automatically logged segments and three completed decisions, giving 50% decision coverage by segment. Physical walk-ins and automatic segments have different units, and their alignment has not been fully annotated. This is a two-person, same-session pilot. Threshold calibration, the full team protocol and cross-camera appearance acceptance remain pending. Numeric summaries and all segment outcomes are under `reports/HuynhNguyenHoaiLoc/week-07/live_adjusted_*`. Raw overlays and embeddings remain private in `data/`.

The requested schedule is 5 Hz. Actual processed rates were about 3.73/3.98 FPS in these door-only runs. DQK's target combined-GPU measurements retain their separate protocol and attribution.

The 0.45 cosine threshold and top-K rule remain provisional. `visible_body` crops need DQK's visibility measurement and cross-camera validation. The standalone CLI owns its in-process queue. The combined application must inject KR's shared queue/state machine. T1, D3, independent D5 and robot acceptance remain open. PR #108 contains overlapping face-landmark changes and the guided webcam enrolment tool. This branch builds from main and does not depend on merging its motion tools.
